Athena
Does the work: runs the SQL, reads and writes the files.
Like a librarian.
Glue Data Catalog
Says WHERE the table is: points at its live metadata.json.
Like the library's catalog card.
Iceberg (metadata/)
Says WHICH files make up the table, and keeps every version.
Like a book's table of contents.
S3 bucket
Stores every file. Has no idea what a "table" is.
Like the library building and its shelves.
Parquet files (data/)
Hold the actual ROWS, stored column by column.
Like the pages of the book.

Reading data

SELECT COUNT(*) FROM trip_events WHERE event_date = DATE '2026-07-07'
1
Athena asks Glue: "where is trip_events?" Glue answers with the live metadata.json.
2
Athena opens it: the table of contents for the current version.
3
The manifests list every file and its date, so Athena skips every file that isn't 2026-07-07.
4
It reads only those few Parquet files, leaves out deleted rows, and returns the answer.
Why it's fast and cheap: Athena only opens the files it needs, even when the table has years of data.

Writing data

INSERT INTO trip_events SELECT … (what cmd/export does every night)
1
Athena writes new Parquet files into data/. Old files are not touched.
2
It writes a new table of contents: new manifests and 00003.metadata.json.
3
It asks Glue to move the pointer from 00002 to 00003. This moment is when the new data goes live.
4
If anything fails before step 3, the pointer never moved, so everyone still sees the old table. Nobody ever sees half-written data.
DELETE works the same way: instead of changing a Parquet file, it adds a small "delete file" plus a new version.

Good to know

  • Every version is kept, so you can query the table as it was yesterday (time travel).
  • VACUUM (weekly, cmd/compact) removes old versions and the files nothing uses anymore.
  • Never edit or delete files in S3 by hand. Always change the table with SQL in Athena, or the table of contents stops matching the files.
  • Our Go code writes no Iceberg files. It only sends SQL.
