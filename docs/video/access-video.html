Rules for the data itself

#
Hashed IDs only

Personal data is stored as vehicle_id_hash, never a plain number plate or name. Every personal-data table keeps that ID so it can be erased.

✗
No test data

Synthetic CITY_ZZ / Cityville rows never enter the production lake. They're filtered out by city code.

⏳
Retention

Files move to cheaper storage over time: Intelligent-Tiering at 30 days, raw to Glacier IR at 365 days. Query results are deleted after 7 days.

⌫
Right to erasure

DELETE the vehicle's rows in raw and curated, then VACUUM so no old version can bring them back. The result is recorded in a manifest.

=
Every run is checked

Row counts and checksums must match Postgres (and raw ↔ curated), or the run fails and an alert email goes out.

§
Per-jurisdiction law

DPDPA (India), GDPR (Budapest), PIPEDA (Toronto). Retention periods are set per jurisdiction and still need sign-off.

Rules for security and governance

🔒
Encrypted everywhere

Lake files and query results use SSE-KMS with our own customer-managed key.

⛔
Never public

S3 Block Public Access is on for the lake bucket. There are no public endpoints.

👁
Access is logged

S3 server access logs go to a separate logs bucket. Every export writes a manifest as evidence.

1
One role per team

No shared logins. Each team is fenced into its own role and workgroup, and the pipeline has its own separate role.

✍
CTO sign-off

Any cross-account access, public endpoint, or wider IAM permissions needs a written recommendation and CTO approval first.

▦
Column-level later

Access is per zone today (IAM). Lake Formation is the plan if column-level control is ever needed.

Who uses the lake

docs/DL-PLAN-001-brief.md · s2, s6
Three reader teams, each with its own access:
• Analytics: mtsai-analytics
• Forecasting: the forecasting / AI workstream
• Audit: auditors and the audit service
One writer: the pipeline jobs that run on ECS (export, curate, compact, trim, erasure).
City dashboards (GR Demo, Control Center) are also named as consumers in the brief, but they don't have their own workgroup yet.

A role and a workgroup per team

terraform/modules/athena-workgroup/main.tf
resource "aws_iam_role" "consumer" { for_each = var.consumers # analytics, forecasting, audit name = "mtsai-datalake-test-${each.key}" } resource "aws_athena_workgroup" "consumer" { enforce_workgroup_configuration = true }
A team member (or service) assumes the team's role, and can then only run queries in that team's workgroup.
Still to do: each role currently trusts the whole AWS account. Narrowing it to the real people and services for each team is an open TODO in the Terraform.

Guardrails per team

terraform/modules/athena-workgroup/variables.tf
analytics = { cutoff = 5 GB, budget = $50 } forecasting = { cutoff = 5 GB, budget = $50 } audit = { cutoff = 10 GB, budget = $25, raw_zone_read_access = true }
• A query that scans past its limit is cancelled by Athena.
• Going over the monthly budget sends an email alert.
• Results land in the team's own athena-results/<team>/ folder. Other teams can't list it, and it's deleted after 7 days.

Five checks on every query

IAM policy statements (athena-workgroup/main.tf)
1-2 AthenaWorkgroupOnly 3 GlueCatalogRoot + GlueCuratedRead GlueRawRead # audit only 4 CuratedZoneGet / List # prefix-scoped RawZoneGet / List # audit only AthenaResultsReadWrite # own folder 5 ResultsDecrypt # KMS
A query has to pass all of these. Each one was added after a real permission failure showed it was needed, and it's written down in STATUS.md.

The pipeline is the only writer

terraform/modules/export-task/main.tf
The export task role can:
• read Postgres as a SELECT-only user (password from Secrets Manager)
• write raw/, curated/ and export-manifests/
• run Athena in its own pipeline workgroup
• delete files only for VACUUM and erasure
Reader teams have no write permission at all, so nobody can change lake data by accident.

Where these rules come from

docs/classification-table.md
Every source table is placed in a class (hot, warm events, cold reference, derived, test). The class decides what the lake keeps and for how long.
Status: draft. Retention periods are still placeholders, and the table needs sign-off from the CTO and the GDPR (Budapest) and PIPEDA (Toronto) compliance owners.

Governance

docs/DL-PLAN-001-brief.md · s6, s12
Access is controlled with IAM: one role per team, scoped by zone.
These always go to the CTO first, with a written recommendation:
• cross-account access or a public endpoint
• IAM permissions wider than the org handoff
• promotion to the prod account
